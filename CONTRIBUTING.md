# Contributing

Testing Thursdays resources should remain practical, stage-aware, evidence-driven, and easy to use live.

## A good resource answers

- Who is this for?
- When should it be used?
- When should it **not** be used yet?
- How long should it take?
- What inputs are required?
- What steps should the founder take?
- What artifact, decision, test, or measurable outcome should result?
- What are the common mistakes?
- What is the next step?

## Preferred front matter

```yaml
stage:
project_type:
blocker:
skill_level:
risk_level:
time_required:
output:
requires_target_users:
requires_code:
last_verified:
status:
```

Use `last_verified` for time-sensitive tools, pricing, startup programs, APIs, or platform-policy guidance.

## Good contributions

- reusable test packs;
- better prompts grounded in observed testing behavior;
- examples of bugs converted into regression tests;
- GTM experiments with measurable outcomes;
- launch-blocker diagnostics;
- short skills that produce artifacts;
- facilitator formats that improve session quality;
- low-cost tool guides with “use when / don't use yet” advice.

## Avoid

- generic startup inspiration;
- huge checklists with no prioritization;
- tool lists without use cases;
- feature brainstorming presented as user evidence;
- advice that encourages bypassing security, compliance, privacy, financial, or platform controls;
- synthetic AI feedback presented as real market validation.
